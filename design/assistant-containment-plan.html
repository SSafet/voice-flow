Assistant containment

Replacing the three trust presets with an OS-enforced boundary — design for review, nothing built yet.

The load-bearing claim, tested rather than assumed.

Agent-framework permissions cannot contain a shell: once bash runs, rm becomes a Python script and rules on command text are theatre. So containment moves below the agent, into the macOS Seatbelt sandbox, which is inherited by every descendant process.

I ran the escape attempts against a real profile on this machine (macOS 26.2) before writing this. Direct writes, rm -rf, a model-written Python script, a nested shell, a detached background daemon, an SSH-key read, and a raw exfiltration socket — all blocked at the syscall. One rule I wrote was wrong and let traffic out; it's fixed and re-verified below.

Goal

The assistant can do anything you'd expect a capable helper to do — read anything, run anything, reach the network, use Notion — without any prompt, except one: when it wants to work in a folder it hasn't been granted. Meanwhile the four things you named as actually dangerous become impossible, not "asked about".

Failure condition, so this is measurable: if after the change any of the six escape tests below succeeds, or if a routine ask from your history still needs a prompt, the design failed.

The residual risk, stated plainly

Host-level control stops exfiltration to an attacker's server. It does not stop exfiltration through a host you've already allowed — a compromised agent could write secrets into a Notion page. Nothing short of cutting network entirely closes that, and the cheap mitigation is the row above it: if secrets are unreadable, there is nothing worth sending. I'm accepting this rather than hiding it.

The workspace grant — your one accepted prompt

Today the runtime's working directory is silently assistant.directory (Agent.swift:647). Under this design the workspace is explicit and is what the sandbox is built from, so changing it is the one moment the security boundary actually moves — which is exactly the prompt you said you're fine with.

Before

Every bash command → a modal that says "Permission requested". You approve blind, dozens of times, and learn to click through.

After

"FLORA wants to work in ~/repos/pantria." Approve once. Everything inside is then silent — edits, deletes, commands, network. Grants persist per assistant.

The bug worth dwelling on.

My first profile used (allow network* (local ip) (remote ip "localhost:*")). That reads as "localhost only" and is wrong — (local ip) matches outbound connections too, re-opening everything. T4b[4] connected to 1.1.1.1:443. The correct form is below. This is the difference between a design that claims containment and one that has it; the same class of mistake is why the validation contract exists.

; wrong — silently allows all egress
(deny network*)
(allow network* (local ip) (remote ip "localhost:*"))

; correct — verified T7
(deny network*)
(allow network-outbound (remote ip "localhost:*"))
(allow network-bind    (local ip  "localhost:*"))
(allow network-outbound (remote unix-socket))

Why nothing you use today breaks

The network posture sounds restrictive and isn't, because the runtime environment already passes HTTPS_PROXY and HTTP_PROXY through (Supervisor:589 allowlist). Point them at the local proxy and every well-behaved client follows: OpenCode's webfetch, MCP's HTTP client, curl, git, pip. No per-tool brokering. Tools that ignore the proxy — which is what injected code would do — hit the kernel denial.

Open questions

  • Default workspace grants. I'd seed ~/repos, ~/Desktop, ~/Downloads, ~/.config/voice-flow so today's blocked asks work immediately. Say if you'd rather start empty and grant on demand.
  • Egress allowlist default. Log-and-allow by default (you see everything, nothing blocked) versus allowlist-and-deny. Log-and-allow is friendlier; deny is safer. My lean is log-and-allow, since secrets being unreadable is the real control.
  • Codex backend. It has its own sandbox (workspace-write, Codex.swift:92) with network_access=true. Do we bring it under the same profile, or let the two backends differ? Leaving it means the weaker posture stays reachable from the conversation header.

Assumptions

  • ASSUMED OpenCode's internal webfetch honours HTTPS_PROXY. curl does (T10) and the underlying runtime normally does, but I haven't run OpenCode's own fetch through the proxy. If it doesn't, that one path needs a Voice Flow tool — nothing else changes.
  • ASSUMED The bash permission event carries the command in title. The type is verified (title: string in the 1.17 SDK); that it holds the command specifically is inferred from how the TUI renders it. One live run confirms.
  • ASSUMED Seatbelt stays available. sandbox-exec is deprecated-but-working on macOS 26.2 and is what Codex depends on today, so this risk is already one you carry.
  • VERIFIED everything in the Feasibility table, run on this machine, output quoted in the session.

Reverting

Every piece is additive and independently switchable. Dropping the sandbox-exec prefix from the launch line restores today's behaviour exactly; the profile file becomes inert. The proxy is off when the env vars aren't set. Nothing here migrates data destructively — the only stored-state change is the job store's trust-profile column, which is read-mapped rather than rewritten.
