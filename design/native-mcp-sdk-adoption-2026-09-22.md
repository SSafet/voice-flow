# V6 native MCP adoption decision

Based on platform a486be9; isolated branch codex/native-mcp-sdk. This change replaces the native handwritten JSON-RPC handler with official Swift MCP SDK 0.12.1 (a0ae212ebf6eab5f754c3129608bc5557637e605). It adds no server, runtime, scheduler, permission store or thread store.

## Boundary frozen before live integration

- Keep the existing LocalAPIServer listener and all TTS/native API routes. Move its definitions, including the pure TTS API input payload, from TTS.swift into LocalAPI.swift so the exact production HTTP adapter can be compiled and exercised independently. This move is not deletion savings. Hummingbird is already pinned but unused in this base; replacing every local route is a separate gate.
- One SDK `Server` and `StatelessHTTPServerTransport` per existing native voice identity; SDK explicitly supports externally managed sessions. Existing JSON clients (`tests/e2e_agent_harness.py:mcp_json`) send Accept application/json and would break against SDK's SSE-only stateful transport. GET remains 405. DELETE releases the matching peer and notifies the existing session-end UI callback.
- SDK owns request/notification decoding, error envelopes, dispatch, typed tools/results, HTTP origin/content/accept checks, version negotiation and request cancellation. The retained MCPSessionRegistry is voice routing/engagement identity, not canonical history. Unknown legacy IDs re-adopt; headerless calls share anonymous. Neither grants captured access.
- Known requested versions (2024-11-05, 2025-03-26, 2025-06-18) retain their revision. New/unknown requests follow SDK negotiation, currently latest 2025-11-25. No local negotiation fork. SDK validation now rejects incorrect Accept/Content-Type/origin instead of silently accepting them.
- Only the existing App.swift MCP setup callback signatures change. Earliest launch guard stays untouched. Tool callbacks get a request-scoped cancellation signal; long-held native inbox/question waits release without consuming another session's messages. SDK cancellation is advisory: return a bounded cancelled tool result because throwing CancellationError suppresses the response and parks the SDK JSON HTTP waiter until disconnect.
- Five `captured_*` tool schemas route through the existing CapturedReadService and shared query. Images are reduced there (400 KB each, 12 images/4.8 MB total); SDK carries image blocks with captureId and decoded width/height metadata. Hints remain separate text blocks, preserving structuredContent/images.
- No implemented external-MCP observe-grant authority exists in this base. `authorizeCapturedRead(MCPSession)` is explicit, nil/default-deny and rechecked during reads/images. The real future device-channel authority must bind authenticated calling thread/device/allowed client; client `_meta`, request arguments, locality and assistant dial never grant access. Unconnected access returns a visible `captured_access_unconnected` result. Do not call this gate complete until real authority is wired.
- Overlay reads/mutations are bounded to the calling session; user/system/other-session overlays cannot be listed, replaced or bulk-cleared. Existing embedded overlay ownership is reused as the rule; no UI/input redesign.

## Evidence scope

Source tests use temporary config roots and an isolated loopback port, compile the production HTTP/MCP/inbox closure and a separate captured-reader closure. Full app build, signed native question UI, current Claude Code/Codex client and long-lived external listener acceptance belong to root's integrated gate. The `~/.claude/skills/communicate-with-user/scripts/vf` path currently advertised by report_to_user is absent on this host; that advertised listener cannot be marked tested.

Official sources inspected September 22: [SDK](https://github.com/modelcontextprotocol/swift-sdk/tree/0.12.1), its HTTPServer transport sources, Server cancellation and supported-version negotiation. No source code fork or custom SSE parser is introduced.

## Capability and adoption accounting

Input/Output modality/convenience: retained session-targeted voice/report/wait plus bounded capture images. Infra parallelism/connectivity: unrelated calls continue during held waits; disconnect/cancel releases exactly one request and refresh reuses identity. Data generated: the existing derived read service is exposed with its limits and preserved originals. Access + Efficacy tools/guardrails: typed SDK boundary, observe authority remains default-deny, and public overlay ownership checks plus mutation are serialized. Consumption/Control: named engagement, explicit cancellation/unavailable listener results. Triggers, fetched/persistent source ingestion and human sharing are unchanged and not acceptance claims for V6.

The old MCP.swift handler/envelope section is 100 lines removed. The original 378-line LocalAPI block plus 8-line TTS API payload move files (386 lines, not retired). SDK/new adaptation is accounted separately: MCPHTTPHost owns the necessary per-voice-peer bridge to the SDK; MCPToolCancellation bridges blocking native calls; MCPCapturedCatalog/Reader bind existing queries; MCPOverlayScope enforces public tool ownership. This branch adds capability and verification and does **not** claim a net line-count reduction. No vendored SDK source was added. Package resolution adds pinned MCP 0.12.1 and its EventSource 1.5.1 dependency; other existing pins are unchanged.

Implemented/source-validated in an isolated branch; not integrated, deployed or user-accepted by this receipt. The test harness uses the real HTTP listener/SDK/inbox and real GRDB/query/ImageIO source closure. Native report UI handlers are parsed but not compiled in these focused fixtures; the long-held question fixture exercises the same production cancellation primitive with a synthetic callback, not AppKit interaction. The 4-hour identity expiry check uses an injected clock, not a 4-hour soak. Current Claude Code/Codex clients, absent vf listener, actual signed native question/overlay UI, complete shared runner/catalog registration, and authenticated channel observe-grant/tunneled-image wiring remain explicit root gates. No daily data or installed app was touched.
