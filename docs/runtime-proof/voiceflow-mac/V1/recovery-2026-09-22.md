# V1 launch gating and recovery — 22 September 2026

This change completes the recovery/startup boundary reviewed in `design/v1-integrity-review-2026-09-22.md`. It does not migrate legacy history/Today or adopt the V3 runtime launcher.

## Storage mechanism and ownership

GRDB 7.11.1 remains the database owner. Its `DatabaseMigrator.hasSchemaChanges`, completed migration prefix, transactions, and online backup are used directly. SQLite's system `.recover --ignore-freelist` is a salvage operation; recovered bytes are staged and rejected unless schema, integrity and foreign-key checks pass. No additional storage framework is introduced.

A lost ledger is reconstructed only for the explicitly listed schema-only migrations `0001 store meta` and `0002 thread store`, and only when GRDB proves the complete corresponding schema (including indexes and triggers). Unknown migration IDs, missing required schema, and broken references are refused. Future data migrations must never be added to that inference list merely because their schema looks the same. See the official [GRDB migrator source](https://github.com/groue/GRDB.swift/blob/v7.11.1/GRDB/Migration/DatabaseMigrator.swift), [SQLite online backup](https://www.sqlite.org/backup.html), and [SQLite recovery limits](https://www.sqlite.org/recovery.html).

## User-visible behavior

The app runs `ThreadStoreLaunch` before creating the normal UI, assistant, backend, hotkeys, or sync services. `ThreadDatabase.shared()` refuses access until an explicitly verified canonical pool is installed. Startup errors show a retry window; damaged history shows native Restore Newest Backup, Try Repair, Start Empty and Show in Finder actions. Start Empty requires the native confirmation. Closing the recovery window quits safely.

A pending recovery record is written and synchronized before the damaged main database and WAL/SHM are renamed. Interrupted renames resume; restarting while recovery is pending cannot create a new empty database. Malformed or mislocated recovery metadata fails closed. Blocked shutdown does not flush uninitialized legacy history. Damaged files remain after every recovery choice, and attachment sweeping is suspended while such files exist.

Every pending schema upgrade gets its own verified snapshot, even after that day's daily backup. Upgrade snapshots are retained separately; only ordinary daily snapshots rotate to seven. Backup candidates are checked before publication. Restore, repair and Start Empty prepare a verified database beside the destination; they never truncate the old active file to discover afterwards that recovery failed. Atomic renames and directory synchronization order publication before the gate is cleared.

## Signed QA interface and reproduction

`ThreadStoreQA.swift` and `/__qa/thread-store*` are compiled only with `VOICE_FLOW_QA`; the existing loopback QA server requires the rotating 0600 bearer token and an isolated configuration root. The GET dump is read-only and reports state, file paths and hashes, migrations, installation/home ID, project/thread records, counts and canonical record hashes. The seed/backup controls operate only on that isolated store. Recovery controls click the actual native window button and invoke its normal controller callback.

Run `./scripts/v1-observe-damage-drill.sh --root /tmp/<new-empty-directory>` after `uv sync`. It refuses any port except 18793, any root or QA bundle outside /tmp, and any nonempty root. By default it uses the existing signed QA installer with an explicit temporary app destination; `--app /tmp/<signed-QA-bundle>` reuses a verified QA bundle. No daily app installation, owner configuration, production port, credentials or paid model is used.

The drill creates a project, a thread and 12 Unicode items; takes a backup; terminates cleanly; overwrites 4 KiB at offset 4096; observes and renders the recovery window; proves unauthenticated access is denied and ordinary app controls/canonical reads are blocked; restarts while still blocked; clicks Restore; compares installation identity, counts and record hashes; verifies the damaged file's exact SHA-256 remains; and restarts the restored app once more.

## Remaining boundaries

SQLite salvage may lose records that cannot be recovered; no exact-history claim is made for Try Repair. The original damaged files are always retained. The byte-for-byte logical history comparison in the drill applies to restoring the verified backup. Legacy importer/Today reconciliation and V3 turn consumption remain separate work; this change only establishes the safe canonical launch/recovery boundary.
